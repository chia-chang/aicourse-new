# 補貨檢查

> 這是**挖空模板**。標 ★ 的地方要你自己填。
> 重點是「數字一定要從盤點資料抄，不能自己編」，而且每個數字都要能驗算。

## 什麼時候用

- 跑完 `npm run simulate`，要決定下一版策略每樣菜備幾份時
- 在瀏覽器玩完一天，想看「倉庫盤點」頁的結果該怎麼調整時

## 資料從哪裡來

在 `web-lab` 資料夾執行：

```text
npm run simulate -- plans/策略檔.json --json
```

每一天的 `inventory` 欄位，是那天每樣上架的菜的盤點：

| 欄位 | 意思 | 怎麼驗算 |
|---|---|---|
| `name` | 菜名 | — |
| `stocked` | 早上備了幾份 | 策略檔裡的 `qty` |
| `sold` | 賣出幾份 | 打烊報表 |
| `waste` | 報廢幾份 | 備貨 − 賣出 |
| `missed` | 賣完之後，還有幾位客人想買卻沒買到 | 客人卡片上「賣完了」的數量 |
| `status` | `ok` 正常、`out` 缺貨、`over` 報廢過多 | 規則書「倉庫盤點」 |
| `suggest` | 明天建議備幾份 | 賣出 ＋ 沒買到 |

## 步驟

1. 執行上面的指令，讀每一天的 `inventory`
2. 先驗算：`waste` 有沒有等於 `stocked − sold`？對不上就停下來回報，**不要用錯的資料做建議**
3. 挑出 `status` 不是 `ok` 的菜
4. ★ 建議備貨量要不要再調整（例如：明天客人比較多的日子，要不要多備幾份？多備幾份？）：用使用者提供的「倉庫盤點」資料或上述試算結果，先逐筆完成下方的驗算檢查，再依有效的狀態挑出異常。以「賣出 ＋ 賣完後沒買到」為備貨基準，並列出「基準 − 原備貨量」說明增減幾份。若有可核對的來客變化數據及支持調整這道菜的依據，才另列調整算式與整數取法。資料不足時採用基準。若要合併成整日方案，核對最多上架 4 樣、總備貨最多 80 份，以及備貨成本加宣傳費是否超過手上資金。缺少整日驗算所需資料或超限時，指出問題，保留逐菜基準供店長參考。
5. ★ 同一樣菜連續幾天都缺貨或報廢過多，要怎麼提醒：按天次排列同一道菜的有效盤點。相鄰兩天以上同為缺貨或同為報廢過多時，列出起訖天次、天數（迄日 − 起日 ＋ 1），以及每天的沒買到人數或報廢份數與備貨基準。跨到缺資料、驗算失敗、正常或不同狀態的天次時，該段連續紀錄結束。
6. 用下面的回報格式回報

## 回報格式

```text
策略檔：
驗算結果：通過 / 第 N 天的 ○○ 對不上（寫出哪個數字）
第 N 天：
  缺貨：菜名 備 … 賣 … 沒買到 … → 建議 …
  報廢過多：菜名 備 … 賣 … 報廢 … → 建議 …
★ 備貨增減與依據：逐菜列出原始數字的來源、原備貨量、備貨基準與增減算式。若另有調整，附調整依據與算式。驗算失敗時，在「驗算結果」列出天次、菜名、問題欄位、原值或缺漏及應有值或判定依據。
下一版每天建議的備貨量：
```

## 寫完檢查

- [ ] 每一個數字都能在盤點資料裡找到
- [ ] ★ 我再加一條檢查：逐筆確認天次、菜名和各盤點欄位齊全，備貨、賣出、報廢、賣完後沒買到、明天建議備貨皆為非負整數。確認賣出不超過備貨、報廢等於備貨減賣出，且有人因賣完沒買到時，賣出應等於備貨。依規則書核對狀態：沒買到人數大於 0 為缺貨，否則報廢達 5 份為報廢過多，其餘為正常。核對明天建議備貨等於賣出加沒買到人數。

## 不准做的事

- 不准修改任何檔案（這個 Skill 只讀不寫，要改策略交給 result-review）
- 不准自己編數字，或用「大概」、「差不多」帶過
- ★ 我再加一條：不得用猜測補齊資料。原始數字只採用使用者提供的盤點或上述來源，衍生數字一律列出算式。缺漏或矛盾時依回報格式指出問題，停止對該筆提出備貨建議。其餘有效盤點仍可分析。
